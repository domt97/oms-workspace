repos): never renumber or reuse one. When an item is resolved, delete it (or turn it into an ADR) in the same PR; when it
is half resolved, rewrite it to what is still open. A number that is not in this file is closed. History is in git, not here. Business questions (Q-ids) are in

## Local infrastructure

Both connectors use a publication created by script (`publication.autocreate.mode: disabled`), so a dedicated user needs no ownership: REPLICATION, CONNECT on the DB, USAGE on its schema, SELECT on `outbox_events` and `debezium_heartbeat`, INSERT + DELETE on `debezium_heartbeat`, USAGE on `debezium_heartbeat_id_seq` (`development` `docs/connectors.md`).

25. **Local AWS resources drifted, and the import bucket comes from the request.**

## Correctness (stores-service)

36. **No cap on `productIds`** in create-collection (body) and add/remove-products (query string). Cost grows with the list: the query string length on add/remove, the size of the `IN` list in the product check (pgjdbc rejects more than 65,535 bind parameters), and one `nextval` per link row (`product_collection_seq`, `allocationSize = 1`). Decide a maximum (new API rule) and enforce it with `@Size`. Add/remove now use one native statement with the whole list (`IN`); a conflicting add still consumes a `product_collection_seq` value (harmless).
37. **Product search and collection products sort in memory.** Both filter by `store_id` (`idx_store_products_store`, V3) and order by `created_at, id` or `name, id`, so every page reads and sorts all of the store's products (collection membership is checked through `uk_product_collections_collection_product`, V6). Fine at the assumed hundreds to a few thousand products per store; add `(store_id, created_at, id)` / `(store_id, name, id)` indexes if EXPLAIN shows large sorts. Name order follows the database collation (local image `en_US.utf8`): confirm Vietnamese names sort as expected on the real database.
38. **Currency is not tied to a market yet** (BR-STO-09, decided 2026-10-31: the market fixes the currency and prices are set per market — not built): create-store and update-configs accept any 3-letter code, and SKUs accept any 3-letter code (decided 2026-10-28; only VND prices must be whole, stores-service#47). oms-web always sends `VND` and assumes it (`domain/money.ts`). Nothing stops one product mixing currencies: `StoreProduct.getMinPrice/getMaxPrice` compare raw amounts across currencies and `getCurrency()` returns the first SKU's, and product search filters price ranges without the currency (`StoreProductPersistenceAdapter`), so USD 9.99 matches a VND 0–10,000 range. To build with markets: derive the store currency from its home market, require each price to use its market currency, and filter price ranges per market currency. Also, Excel import has no bean validation, so a weight/size above `NUMERIC(10,2)` fails the whole import with a database error instead of a clear message.

31. **`Store.ownerId` is a `CustomerId`** (`stores.owner_id`): a store's "owner" is modelled as a customer. With merchants and (later) merchant members (BR-MER-07) this field is redundant and mistyped; drop it or replace it when members are built.

33. **Merchant self-registration is public with no authentication or rate limit.** `POST /v1/store/merchants` lets anyone create merchants and reserve codes. Business side: Q36 (owner link through identity), Q37 (KYC / PENDING). Until identity exists, do not expose the endpoint outside the local network.
34. **The storefront (oms-web) uses seller endpoints because there is no public catalog yet.** oms-web aggregates merchant-scoped stores-service calls over a bounded list of shops and reads `GET /v1/inventory/inventories/products/{productId}`, which is unscoped (item 6) and returns on-hand, reserved and `merchantId` to the shopper's browser (oms-web shows only a status, BR-CAT-04). Consequences: **the public catalog/search read model (BR-USR-05) must ship before stores-service requires seller authentication**, or the storefront breaks; and a page-size cap or auth on these endpoints is a breaking change for oms-web (oms-web `docs/architecture.md` §4).
43. **Removed SKU rows grow without limit per product.** Soft-removed SKUs stay in `product_skus` (their codes stay reserved, BR-CAT-09) and every update-product loads them. The 100-SKU cap counts only SKUs in the request. Decide a purge or a cap on removed rows if products get edited a lot.
44. **A GET can show version v with SKUs of v+1.** GET product loads the product row and its SKUs/images in separate statements (READ COMMITTED), so an update committing in between shows a mixed state. The next PUT with that version correctly gets 409; consider a fetch join or REPEATABLE READ for GET.

## Reliability (messaging)

17. Kafka DLT exists for inventory's catalog consumers (inventory-service#32: `<topic>.DLT`, contract errors at once, DB outages retried until back), but there is **no alerting on DLT records and no replay tool** (see 40); records are only visible as ERROR logs. The stock commands have DLTs too (`ReserveStock.DLT`, `ConfirmStockReservation.DLT`, `ReleaseStockReservation.DLT`, inventory-service `feature/stock-command-consumers`), with the same gap, and there it matters more: **a command in a DLT gets no reply**, so until tooling exists it is noticed only by the saga's timeout (ADR 0006) and one ERROR line (it carries the command's `requestId` and the record's coordinates, not the payload ids). *Next step:* metric + alert, bounded replay endpoint, longer DLT retention.
18. SQS `reservation-expire` queue has **no DLQ / redrive policy** (`development/docker/infra/local/main.tf`).
30. **Kafka topics are auto-created** with broker defaults (1 partition): `ProductCreated` exists only because the broker auto-creates it. Create topics explicitly (partitions, retention) in `development` before consumers need to scale. The stock command and reply topics (ADR 0006) must be created with partitions before their connectors are registered. *Partly done (development#7):* the stock command and reply topics are created by `development` `docker/kafka/create-topics.sh` (6 partitions, 14 days: local values) before the connectors; `ProductCreated` / `ProductUpdated`, the DLTs and the heartbeat topic `__debezium-heartbeat.store` (1 partition, harmless) are still auto-created. Production partitions and retention remain open. The command DLTs are created by inventory-service itself (`NewTopic` beans, 1 partition, `app.kafka.dlt-replicas`), not by the script. *Listener sizing, also open for production:* each command topic has one listener thread per instance by default (`app.kafka.stock-commands.concurrency`), so a command that is being retried (up to ~35 s of backoff plus its attempts) delays the other partitions of that topic on that instance; raising the concurrency needs a larger Hikari pool (`3 × concurrency + 3` ≤ pool, 10 today). The command listeners poll 5 records at a time so that the worst case of one poll (215 s) stays under `max.poll.interval.ms` (300 s): an argument from the settings, checked by hand only for the lock-timeout case.
40. **No way to resync a product to inventory.** If a `ProductCreated`/`ProductUpdated` is skipped (open question 17) or lost (before stores-service fix/import-transaction, an Excel import could commit products without their event), inventory stays stale until the next update of that product. Add a republish (stores) or resync (inventory) tool. Since stores-service#59 the outbox is always empty, so a lost or recreated `debezium_store_v2_slot` also loses the gap's events for good; until a tool exists the only recovery is a real change (and revert) of each product created or updated in the gap — a plain re-save publishes nothing (`development` `docs/connectors.md`, *Runbook (postgres-cdc)*).
55. **Replication slots in production** (development#7): `max_slot_wal_keep_size` (unlimited by default: a stopped connector can fill the disk), alerts on slot lag / `wal_status` and on the heartbeat of both connectors (`max(beat_at)` in `inventory.debezium_heartbeat` and `store.debezium_heartbeat`; Debezium 2.2 is expected to only log most heartbeat query failures, not tested yet (First application 2026-11-09; runbook test in `development` `docs/connectors.md`)), and who creates the `debezium_heartbeat` tables and the insert-only publications outside local (Flyway migrations of the services, or an ops script).
56. **Dead outbox columns** (contract step after stores-service#59): stores' `outbox_events` keeps `status`, `published_at`, `retry_count`, `last_error` and `idx_outbox_events_status`, and the domain `OutboxEvent` keeps `status` / `retryCount` / `publishedAt` / `lastError` and `OutboxStatus`, although rows are deleted in the same transaction. Drop them in one stores-service PR when convenient (the connector does not read them; check the EventRouter placement list first). The two services' outbox tables also differ (`merchant_id` only in inventory's).

## Scale (inventory-service)

22. **Reservation expiry has a throughput ceiling and no backlog signal.** (Since the stock replies, every expiring inventory transaction also does one set-based movement insert and one batched outbox insert + delete, at most one outbox row per order in it.) Since inventory-service#28 each tick is bounded (keyset pages of 500, 40 s budget), but:
    - `markExpired` updates **one row per statement** (`transitionStatus`), so a sweep costs one DB round trip per reservation. Measured locally ≈ 3k reservations/s; with production latency estimated ≈ 1k/s → roughly 40k per tick (estimate, not measured). If more reservations expire per minute than that, the backlog grows.
    - **Instances do not share the work**: every sweep reads from the start in the same `(expires_at, id)` order. After downtime all instances run (stale-tick drop fails open) and contend for the same rows — safe because of the guard, but no faster than one instance.
    - **No metrics**: only logs. Nothing reports the expired-but-still-`RESERVED` count or the age of the oldest one, so a growing backlog is invisible.
    - A failing inventory near the front of the order (e.g. already-corrupted `reserved_quantity`) is retried first on every tick.
    Options when volume requires it: set-based `markExpired` (`UPDATE … WHERE id IN (…) AND status = 'RESERVED' RETURNING id`) plus one release per inventory; claim pages with `SELECT … FOR UPDATE SKIP LOCKED LIMIT n` so instances split the work; Micrometer gauges (backlog, oldest expired age) with an alert; `CREATE INDEX CONCURRENTLY` for future indexes on large tables.

## Design decisions pending (decide when a feature needs them)

6. inventory-service REST has **no `merchantId`** in path or header, unlike stores-service.
7. `InventoryServiceClient` (stores → inventory) and `PromotionServiceClient` have no adapter.
9. No event for **store** close or status change (`StoreStatusChanged` proposed). Product and SKU changes travel as `ProductUpdated` ([flow](flows/product-updated.md)).
10. `ProductCreatedEvent` is duplicated in both services; no shared schema / schema-registry subject.
11. Consumer group `product-consumer` is a generic name; may collide when more services consume products. Do not rename it (with `earliest` a new group replays all `ProductCreated` history); new consumers use specific names (planned: `inventory-product-updated`).
32. **Merchant status is not enforced outside stores-service.** Inventory (and later order) only know `merchant_id`. When Q35 decides what a suspended merchant may do, publish `MerchantStatusChanged` from stores-service and keep a local copy in the consumers.
46. **`requestId` is not carried on outbound HTTP between services** (no client adapter yet; send `X-Request-Id` from `MdcPropagation.capture()` when one is added). Over Kafka it is carried (ADR 0004).
47. **4xx are logged at ERROR with a stack trace** (`oms-core` `GlobalExceptionHandler.logError`): client mistakes (404, 400) drown real errors. Log 4xx at WARN without the stack.
48. **Dead code in oms-core:** `CoreConfiguration` (`@EnableAutoConfiguration` on a class that is never registered) and unused `RequestLoggingProperties` fields (`logRequestMetadata`, `logResponseMetadata`, payload limits, `skipContentTypes`).
49. **No API-compatibility check for oms-core releases** (ADR 0005). With the downstream job gone, a breaking change shows up only when a service bumps `coreVersion`. Option: japicmp (or Revapi) in oms-core CI against the last release, failing unless the version is a new MAJOR.
50. **`coreVersion` bumps are manual.** Dependabot can open them, but needs a `registries` entry for `https://maven.pkg.github.com/domt97/oms-core` with a Dependabot secret (classic token, `read:packages`; it cannot use `GITHUB_TOKEN`), and its support for a version in `gradle.properties` is uncertain (a version catalog is supported).
51. **`stock_reservation_orders` grows by one row per order and is never cleaned** (ADR 0006: the header is also the tombstone that rejects late commands). A cleanup after N days is safe only when N exceeds the command topics' retention, the DLT retention and the stale-command window. Decide N when volume matters.
52. **`GET /v1/inventory/inventories/stock-movements/{inventoryId}` is not paged.** With movements for every hold and sale (BR-INV-05) a busy SKU gets tens of thousands of rows. Paging the endpoint is a breaking change for oms-web (*Front-end consumers*).
53. **Integration tests (Testcontainers)** for inventory-service exist since inventory-service#39: Gradle suite `integrationTest` (Postgres 16, SQL, constraints, JSONB, lock timeout, races) and the CI job `Integration tests` (Docker of the runner, **not a required check yet**: make it required after it has been green for a while). The outbox is covered too (`OutboxSqlIT`, `StockRepliesIT`, `OutboxFailureIT`, reading the WAL through a `test_decoding` slot). The command consumers' listener methods are covered on the real use cases (`StockCommandConsumersIT`) and the real timeout exceptions against the error handler (`StockCommandErrorClassificationIT`). Still open: nothing runs against a broker — that the listener container applies the `@KafkaListener` settings and the error handler, DLT publishing and topic creation are manual checks (an embedded-Kafka or Testcontainers-Kafka test would close it); stores-service has no integration tests.
54. **A confirm without a reply leaves the saga stuck** (ADR 0006 obligation 3, under review). With delete-after-insert outboxes a lost reply cannot be re-published (the row is gone once it is inserted), and a confirm in a DLT has no reply either. inventory is safe with every choice (a re-sent confirm is decided from the header and line states; a release in any order ends in the state the commands describe — flow `order-stock-reservation.md`, *Inventory's guarantee*). To decide with order-service: re-send the confirm or cancel, how many re-sends; the confirm timeout must be longer than inventory's retry window for one command (≈ 105 s with the current handler — not an upper bound: connection failures retry without limit and a blocking retry delays the partition) and shorter than the time left on the hold (the hold starts at placement, BR-INV-02; with the proposed 10-minute payment window, BR-ORD-07, as little as ≈ 5 minutes may be left; after expiry a re-sent confirm answers `NOT_RESERVED`); metrics/alerts on confirm timeouts and re-sends. Business half: Q42 in `business-rules.md`.
