# Business Rules

> **How to read this file.** Each rule has an id and a status:
> - ✅ **In code**: true today; reference given. Code wins if this file disagrees.
> - 🟢 **Decided**: confirmed by the product owner (date in brackets). Build on it; if code differs, the code has a gap.
> - 🟡 **Proposed**: solution-architect recommendation. **Not decided**; the product owner must confirm or change it.
> - ❓ **Open**: needs a decision; see the question at the end.
> - ~~Struck through~~ **Withdrawn**: a rule the product owner dropped (date given); kept so old references still resolve.
> - *Under review (date, open question N, Qn)*: appended to a status; the status still holds, but ask the user before
>   designing on that rule (`sa-analysis-checklist` §1).
>
> **Agents:** design only on ✅ and 🟢 rules, and on 🟡 rules the user has confirmed in the conversation.
> For ❓ items, ask the user (quote the question id). Never invent a rule. When the user decides, update
> the status here in the same piece of work.

Anything else is `INVALID_REQUEST` for the checkout, without the field's text. cart-service (not built) and oms-web must enforce the same limits; oms-web does not yet (one free-text address field, no caps, open question 68). | 🟢 2026-11-15; 🟢 2026-11-17 (user): field limits. ✅ order-service `PlaceCheckoutValidator` (intake) |
| BR-ORD-16 | **Stock confirmation gates the store.** The store sees an order, and auto-accept or the 5-minute window (BR-STO-05, BR-ORD-08) starts, only after inventory confirmed the order's stock. Any confirmation failure cancels the order and releases it, and the customer is told the items are no longer reserved. A missing reply never cancels: the confirm is sent again. | 🟢 2026-11-15 (Q42, open question 54) |
| BR-ORD-08 | With `autoAcceptOrder` the order goes `PLACED → ACCEPTED` immediately. Otherwise staff must accept within **5 minutes** or the order is rejected automatically (stock released, payment refunded). | 🟢 Q12 (2026-10-25) |
| BR-ORD-09 | Cancellation:<br/>- the customer may cancel until the order is `ACCEPTED`;<br/>- after that, only the store can cancel (with a reason);<br/>- cancelling releases unconfirmed stock and refunds a captured payment in full;<br/>- confirmed stock is returned only if the store marks the goods reusable; the release sent to inventory carries this as `restock`. When the store never touched the goods (auto-reject, BR-ORD-08, or a customer cancel before `ACCEPTED`), order-service sets `restock = true` itself.<br/>- `restock` by end state: customer cancel, auto-reject and a staff reject before `ACCEPTED` → `restock = true` (the goods were never touched); `DELIVERY_FAILED` → `restock = false`, and staff correct stock by hand. | 🟢 Q13 (2026-10-25); automatic `restock` 🟢 2026-11-05; 🟢 2026-11-15 restock by end state |
| BR-ORD-10 | An order has a human-readable number unique per store, separate from its UUID: **`{storeCode}-{yyMMdd}-{seq}`**, e.g. `Q1-261115-042`. The date is the store's local day (BR-STO-03 time zone); `seq` counts that store's orders of the day from 1, zero-padded to 3 digits (more digits if the day passes 999). | 🟢 2026-11-15 |
| BR-ORD-11 | Placed orders are never edited (lines, prices). Changes are cancel + re-order, until a modification feature is designed. | 🟢 2026-11-15 |
| BR-ORD-12 | order-service **orchestrates** the order saga (reserve, payment, delivery booking, timeouts, compensations); other services execute commands and report back with events. Commands travel over Kafka from order-service's outbox (stock: `ReserveStock`, `ConfirmStockReservation`, `ReleaseStockReservation`, key `orderId`); replies come from the executing service's outbox (ADR 0006). | 🟢 Q6 (2026-10-25); transport 🟢 2026-11-05 |
| BR-ORD-13 | After placement, each order of a checkout lives on its own: each store accepts, rejects, prepares and cancels its own order; refunds are per order. | 🟢 2026-11-15 |
